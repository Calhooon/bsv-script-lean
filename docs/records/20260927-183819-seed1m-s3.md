- **bsv-rs: 6 entries, 4 witness lines** (one per shard, column and rule, the smallest; shards 03, 05, 10, 15). Each is a mutation entry that builds, with `OP_NUM2BIN`, an element of exactly INT32_MAX bytes: the attempted 2,147,483,679 = 2,147,483,647 + 32, the element's size plus the stack's per-element overhead (`limitedstack.h:43`).
  - bsv-rs 0.3.30 stops at "resource limit: stack limit 100000000" **under the block word**.
  - The reference decides each entry; the release agrees with the spec on all of them. The four witnesses' own verdicts: invalid `SCRIPT_ERR_INVALID_STACK_OPERATION`, valid, invalid `SCRIPT_ERR_SCRIPTNUM_OVERFLOW`, invalid `SCRIPT_ERR_EVAL_FALSE`.

**Finding (for T3, bsv-rs).** After Genesis, the reference's stack-memory budget on the block path is the consensus value, whose default is `DEFAULT_STACK_MEMORY_USAGE_CONSENSUS_AFTER_GENESIS = INT64_MAX` (`consensus/consensus.h:82` at `879fc8b42`; `docs/PARAMETERS.md:40`). The policy's is `DEFAULT_STACK_MEMORY_USAGE_POLICY_AFTER_GENESIS = 100 * ONE_MEGABYTE` (`policy/policy.h:153`).
- bsv-rs 0.3.30 applies 100,000,000 under the BLOCK word (`ScriptFlags::block`, the `spec` column of `run_diff`). So it refuses, as a resource limit, an element the reference allocates.
- Under the standard word the same figure is the policy default, and bsv-rs agrees on all 1,000,000.
- The authored corpora never reached it: bsv-rs 0.3.30 aborts on none of their 13,254 entries (`docs/records/20260927-174629-diff-bsv-rs-0.3.30-s3.md`). The stack family's `OP_NUM2BIN` rung at 2³¹ (`corpus/INDEX.md` §4) is one past `OP_NUM2BIN`'s own bound, INT32_MAX (`interpreter.cpp:1749–1752`), and is refused before any allocation. The random run landed on INT32_MAX exactly.
