## Method

1. **The two re-reductions removed (the time).** Two declarations that only
   restate the run made the kernel evaluate it again.
   - `staleRunFinal_reachable` was the chain of `Reachable` constructors with
     their indices left to unification. Its kernel check took 95 to 203 s. The
     three run states (`staleRunActivate`, `staleRunWith1a`, `staleRunFinal`)
     were `abbrev`s; they are `def`s now, with the same bodies, and the proof
     goes through one step, `Reachable s → Reachable (staleRunActivate
     (acceptBlock s staleRunContext b rank true).1)`, applied three times. Its
     check is under 0.1 s [M]. Measured along the way: the same `abbrev`s with
     every step's type written out took 222 s, and with the generic step 199 s;
     the `def` copies with the step took under 0.1 s (`/tmp` scratch files,
     not committed). [D] My reading of the cause, from the measurements and
     not from the kernel's source: an `abbrev` on both sides of a comparison is
     unfolded on both sides at once, the two sides stop matching, and the
     kernel ends at a projection of the run, which it evaluates. With `def`s
     the kernel unfolds the higher definition only and the two sides match by
     name.
   - `s6_charter_removal_false` closed `invalidateBlock … = (staleRunInvalidated.1,
     staleRunInvalidated.2)` by `rfl` (33.7 s); it closes now by the pair's eta,
     `(Prod.mk.eta (p := staleRunInvalidated)).symm` (under 0.1 s).
   No statement changed; every proof is sorry-free and every theorem is on the
   list (`make axioms` above). `s6_stale_path_reachable`'s derivation was
   already cheap (a copy checked in under 0.2 s).
2. **The roads measured and not taken.** A structural copy of SHA-256 (fuel and
   `foldl` in place of the well-founded `rounds`, `schedule` and `blocks`) costs
   the kernel the same: 0.37 s against 0.39 s for one compression, so the
   well-founded recursion is not the cost and `Hash/Sha256.lean` stays as it
   is. One `decide +kernel` over both run checks was no cheaper: 244 s in a
   scratch run, where the two checks took 125 s and 57 s apart in the marked
   run, so the two checks stay apart. The
   prefix to 1a alone costs 31 s; the reorganization to 1b and 2b is most of
   the 172 s. [D] Reading, not measured: the header tree's lookups
   (`HeaderTree.get`, `find?` over `BlockIndex.id`, the header hash) recompute
   each stored header's SHA-256d whenever the stored index has been rebuilt by
   an update, because the kernel's cache keys on the term and the header term
   changes form; the #66 leg's record (`docs/records/20261013-073532-s6-66-leg-s1.md`)
   reached the same reading for the compiled executables. Removing that cost
   needs a proved refinement of the tree's lookup (a cached identifier with
   its invariant), which changes the machine and is not this issue's.
3. **The move (the memory).** After step 1 the module is still 229 s and
   28.1 GB alone, about four times the whole rest of the library's cold build
   (60.6 s) and most of the 36 GB box. So it is out of the default library
   build:
   - `lean/BsvChain.lean` no longer imports `BsvChain.Properties.StaleRun`
     (nothing else imported it);
   - `lean/lakefile.toml` declares the library `StaleRunCheck` (roots
     `["BsvChain.Properties.StaleRun"]`) and lists it in `defaultTargets`, so a
     bare `lake build` still builds everything while `lake build BsvChain` and
     the tripwire's lean leg do not;
   - `lean/AxiomCheck.lean` imports `BsvChain.Properties.StaleRun` (its seventh
     import; `AXIOMCHECK_IMPORTS` in `tools/axiom_check.py` allows it), so the
     walk reads its constants and its eight theorems stay on the list;
   - `tools/check.sh`'s axioms leg runs `lake build StaleRunCheck` (refusing a
     sorry in its log) before the axiom check, so the tripwire checks the
     witness on every run, and `make axioms` (which runs the lean leg, then
     the axioms leg) builds it too.
   The walk's pinned text (`WALK_SHA256`) is unchanged: its sentence "the
   imports above are library modules, all built by `lake build`'s default
   targets" stays true because `StaleRunCheck` is a default target.
