## The road [D]

Ten slots per row, each on its own coins so no two signers spend the same outpoint: the hand signer's control
(`signer.rs` `sign_input`, method `hand`) and go-sdk v1.7.2, @bsv/sdk 3.0.0 and bsv-rs 0.5.0 by each of `template`,
`api-default` and `api-scriptcode`. Each row is REBOUND per slot: input i spends output i of the slot's funding
transaction, the prevouts' txid, vout and height rewritten, nothing else (the unit test
`rebinding_moves_only_the_outpoints_and_the_coin_heights`); `params` keep the row's own spend height and era label,
since `Entry::check` binds the label to mainnet heights. The ten rebound corpora (the signer row format) are kept on
[withheld at export: a sibling tree's line]
rebound corpus; the runner refuses a signed transaction whose unsigned form differs from the rebound row. Every signed
transaction is judged by `verifyscript` under the block and the relay words (run_signer's judge, now
`harness/src/signer_node.rs`), then `sendrawtransaction`; after the block, every accepted spend is read back by
`getrawtransaction` with a block hash and the block's height.

**CHAIN AGREES WITH COLUMN** means: accepted and mined when the relay word judges every input valid; rejected when it
does not, with the reject reason's wrapped `SCRIPT_ERR_*` equal to the code of the column's lowest refused input. A spend whose
lock time is not final at the next block (predicted by the `IsFinalTx` rule, `LOCKTIME_THRESHOLD` `script.h:36`) and
whose script is valid is accepted into the node's non-final pool (`validation.cpp:1100-1120`) and not mined: that is a
finality decision outside the script column, counted apart as `finality`, confirmed by `getrawnonfinalmempool`.
This run's runner (`2060c208`) called a rejection whose reason wrapped no script error agreement; the gate is strict
since `33cf7316` (a code-less rejection beside an invalid column is RED, the unit test
`a_rejection_wrapping_no_script_error_beside_an_invalid_column_is_red`). It did not bite here: lane lens-chain-152
recomputed every class strictly from the JSON, and all 400 rejections carry a code equal to the column's [X].

converted to the signer row of its shape (A and C under the `checksig-in-unlock-a` template name, B under

among the 181 above.

## The emitted set [M]

`docs/records/20261017-015216-s3-152-signer-chain-set.jsonl`: 1,810 lines (one per row, engine and method, the 394
unsigned included with `tx_hex: null` and the reason), 3,083,260 bytes, sha256
`f8ff850893db246ddd1387de52563c4c3021ad917b1f614c2b2c083eca0e38be` (written at
`~/bsv/targets/bsv-script-lean-chain-152/set.jsonl` by the run and copied here; under 10 MB, so the set is in the
repository). The format is documented in `harness/README.md` beside run_signer's paragraph. It is the input to #152
step 2 (the Teranode leg, a hazard-class lane). A replay on ANOTHER chain cannot reuse `prevouts[].outpoint`, `tx_hex`
or `funding_tx_hex`: the outpoints name this instance's funding transactions, which spend coins of a chain that no
longer exists, and every signature commits to them. It reuses `id`, `engine`, `method`, `prevouts[].script` and
`satoshis`, and `reference_verdict`, `reject_token` and `reject_code` as the expected class; it funds those scripts and
amounts on its own chain, rebinds the row of `corpus/signer/` (or of `corpus/xsig-144/`, converted) to its coins and
re-signs by the same engine and method; `tx_hex` serves only as the template of what was signed (version, lock time,
sequences, outputs).
