**What the ladder says about #53.** Every number in these locks is one byte (`OP_1` and its neighbours), below the limbs, so the
ladder measures the codec's cost on small operands, not its gain (the gain is on the siblings' locks, 2.3× to 2.6× in user time:
`docs/records/20260929-085123-codec-53-s1.md`). That cost: from 500 kB to 128 MB, 0.3 % to 0.75 % more instructions (the limb
codec's size tests and one more branch on a one-byte operand), and at 256 MB 0.06 % fewer; the walls within 4.3 % either way from 2 MB up (below that they are a few hundredths of a second).

**The reach, restated `[M]`.** Both evaluators judge the 255,999,976-byte lock (a stack 4,654,545 deep, every compiled depth
test in each 55-opcode step) valid on the block path: the limb codec in 31.02 s, #50's in 31.35 s, the same two minutes. The
peak memory footprint is 21.82 GB for both and **linear: 86.0, 85.5, 85.4, 85.3 and 85.3 bytes per lock byte** at 16, 32, 64,
128 and 256 MB. The resident set tracks it up to 128 MB and falls below it at 256 MB (17.02 GB and 17.73 GB against 21.82 GB),
where the box's compressor holds the rest: the page reclaims are 3,842,870 and 4,362,207 there against 666,130 and 666,120 at
half the size. **So #50's "the peak some 57 to 85 bytes per lock byte" read the resident set, which the box's memory pressure
moved; the footprint does not move** (the first run's 256-MB steps, beside another 20-GB-class leg: resident sets 14.11 GB and
14.73 GB, footprints 21,824,831,376 B and 21,824,749,432 B). The time is 0.10 to 0.12 s per million bytes from 16 MB up. A
lock of the consensus size class (inside the 1,000,000,000-byte transaction, `consensus.h:29`) then needs some 86 GB of memory
