## The follow-on: the element's representation [EST]

`Bytes` is `List UInt8`: one cons cell per byte, some 24 bytes each on Lean's runtime (an object header and two
pointers, the byte boxed in the pointer) [EST], so an element costs some 24 times its length, and `num2binPad`'s
`reverse` and `++` hold a second list while it is built. [M] The 2147483647-byte width above shows a peak memory
footprint of 68.9 GB (some 32 bytes per byte) and a resident 30.6 GB on the 36 GB box. Under the consensus column's
`INT64_MAX` the reference itself builds a 2 GB element for such a spend; the spec builds the same element at some 24 to
32 times the size [EST], so any spend that pads to a width above about 1 GB under the consensus limit stays a 30 GB,
100 s evaluation. A 200 MB element (twice the relay limit, admitted at consensus) is some 4.8 to 6.4 GB resident
[EST]. Cure: a packed representation (`ByteArray`) for the implementation state's elements, with an abstraction lemma to
`List UInt8`, or a per-process memory bound on the campaign's spec stage. Not solved here.
