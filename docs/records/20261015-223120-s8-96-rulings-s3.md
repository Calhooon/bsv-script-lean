## 3. The one difference, and the soft-freeze path traced at both pins [SRC]

`tl.soft-freeze`, proposed `dropped`, ruled `gap` (`ruling.owner_reason`). The reference, bitcoin-sv `6504a3af`: a
block whose input spends a consensus-frozen output fails `CheckInputs` with `REJECT_SOFT_CONSENSUS_FREEZE` and
`ConnectBlock` soft-freezes it for `-softconsensusfreezeduration` blocks (`src/validation.cpp:3402-3406`, the freeze
`:3720`); the duration is a setting, default 3 (`src/validation.h:219`), 0 holding the block indefinitely
(`src/init.cpp:1214-1221`); a soft-frozen block "can't be added to best chain as long as it doesn't receive enough
descendant blocks to pass the freeze threshold" (`src/block_index.h:283-285`). Teranode `4edb60a4`, traced by
`git show` at the commit:

1. the alert service's `AddToConsensusBlacklist` (`services/alert/node.go:274`, row `rl.alert-service`) calls the UTXO
   store's `FreezeUTXOs` (`:346`), which sets the output's spending id to FF...FF
   (`stores/utxo/aerospike/alert_system.go:71-77`);
2. a spend of that output is refused with `ERR_UTXO_FROZEN` (`stores/utxo/aerospike/spend.go:1103-1107`, the Lua
   `isFrozen` arm `stores/utxo/aerospike/teranode.lua:406-414`; the SQL backend the same, `stores/utxo/sql/sql.go:2435`);
3. the validator returns the failed spend as a processing error (`services/validator/Validator.go:1248`), wrapped again
   by subtree validation (`services/subtreevalidation/SubtreeValidation.go:433-435`);
4. `errors.Is` matches by code along the chain (`errors/errors.go:181`), and `ERR_UTXO_FROZEN` is not `ERR_TX_INVALID`,
   so the level loop records it as a processing error, not an invalid transaction
   (`services/subtreevalidation/check_block_subtrees.go:1410`, `:1421-1428`, `:1474-1475`);
5. block validation's subtree step returns that error (`services/blockvalidation/BlockValidation.go:2071`, the
   invalid-transaction branch `:2123` not taken, `:2161`), before optimistic mining (`:2182`): the block is not
   accepted and not stored invalid.

Not traced: the legacy-sync path (`services/legacy`), and what a retry does with the same block (each retry meets the
same frozen spend). So the two alert-following nodes hold the same tip while the reference's hold lasts (neither
selects the block) and can hold different tips once it lapses, the reference selecting the frozen spend's branch when
it leads and Teranode never accepting it [D, read from source, not witnessed]. #94's measured leg is where it is
witnessed. The lens's replacement wording ("a block that spends it is refused, never held [D: the block path into the
spend not traced]") is superseded by this trace: the path is traced, and "refused" is "not accepted and not stored
invalid".

A gap row names the view it breaks (#96's done-bar); the row's `breaks` reads [D]: #67's `minedActive h` and
