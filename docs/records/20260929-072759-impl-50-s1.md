## (1) The representation and the refinement

**The representation** (`lean/BsvScript/Impl/State.lean`). `IState` has `Machine.State`'s fields with the main stack an
`Array Bytes` held bottom-first, its top at `back`, as SV-node's `LimitedStack` holds its vector (`limitedstack.h:88`): the
element `k` below the top is `a[a.size - 1 - k]` (`stacktop(-(k+1))`, `limitedstack.cpp:226–233`), the depth is `size`
(`307–310`), a push and a pop are at the end. The alt stack stays a list (only its top is touched). `IState.abs` reads an
implementation state as the spec's (the array reversed into the top-first list, every other field copied), `ofState` goes
back, and `ofState_abs` proves `abs` loses nothing.

**The refinement, the chain of theorems** (all in `lean/AxiomCheck.lean`):
- the helpers, each commuting with `abs`: `pushElemI_abs`, `popElemI_abs`, `topAtI_abs`, `swapTopI_abs`, `eraseTopI_abs`,
  `insertTopI_abs`, `pushCountI_abs`, `needI_abs`, `toAltI_abs`, `fromAltI_abs` (over `reverse_set`, `reverse_eraseIdx`,
  `reverse_insertIdx` and the array lemmas `topArr_eq`, `setTopArr_eq`, `eraseTopArr_eq`, `insertTopArr_eq`);
- every family function restated over `IState` and proven to compute what the spec's computes on the state it stands for
  (`execStackI_abs`; `unaryI_abs`, `binaryI_abs`, `withinI_abs`; `bitwise2I_abs`, `invertI_abs`, `shiftI_abs`,
  `equalI_abs`; `catI_abs`, `splitI_abs`, `num2binOpI_abs`, `bin2numI_abs`; `substrI_abs`, `leftI_abs`, `rightI_abs`,
  `lshiftnumI_abs`, `rshiftnumI_abs`; `hashOpI_abs`, `checkSigOpI_abs`, `multisigLoop_abs`, `checkMultiSigOpI_abs`), and
  each family's hook refining the spec's (`<family>.execI_refines`, with `Refines exec execI` := on every opcode, data,
  environment and state, `(execI op data env s).map HookRI.abs = exec op data env s.abs`);
- the flow opcodes and the step, each the spec's step read back (`execIfI_eq`, `execCltvI_eq`, `execCsvI_eq`,
  `execFlowI_eq`, `execStepI_eq`: `execStepI … s = StepRI.lift s (execStep … s.abs)`, where a `.done` carries the state the
  step started from);
- the loop, `loopI_rel`: the outcome always equal to `Machine.loop`'s, the state at `.ok` standing for its state. The one
  difference is the one the design named: `Machine.loop` returns the step's input state with a failure (`(.err e, st)`), which
  an in-place machine no longer holds, and no consumer reads a state that is not `.ok`'s;
- the two phases written once over the evaluator (`phase2Gen`, `verifyScriptGen`), equal to `Machine.phase2` and
  `Machine.verifyScript` on `Machine.evalScript` by `rfl` (`phase2_eq_gen`, `verifyScript_eq_gen`) and giving the same
  verdict on any two evaluators that agree on every outcome and on every state at `.ok` (`phase2Gen_congr`,
  `verifyScriptGen_congr`); so `verifyScriptA_eq`: `Impl.verifyScriptA execI = Machine.verifyScript exec` whenever
  `Refines exec execI`;
- `lean/BsvScript/Eval.lean`: `opExecI_refines : Impl.Refines opExec opExecI`, `verifyScriptI := Impl.verifyScriptA
  opExecI`, and `@[csimp] theorem verifyScript_eq_I : @verifyScript = @verifyScriptI`, so every compiled call of
  `Eval.verifyScript` after `Eval` runs the implementation.

**The change from the design: the dispatcher.** The design's `opExecI` was `opExec`'s shape, the families tried in turn with
`<|>`. That shape keeps the state alive across the first family's call (the next alternative may need it), so the family
that owns the opcode would receive a shared array and copy it on its first push. `opExecI` asks each family first whether
it owns the opcode (`<family>.owns`, the tests of its `execI`, which read the opcode alone) and hands the state to that
family alone; `dispatch_abs` proves this refines "try this family, else the rest", with `execI_of_not_owns` and
`isSome_execI` per family.
