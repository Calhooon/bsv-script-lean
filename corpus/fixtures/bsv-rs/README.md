[D] The node table's 254 BIP143 rows are each reconstructed by the generator (`bip143_digest`) and compared with the
node's digest before the row is written; a mismatch stops the export. The 746 original-digest rows and the
table's second column (`SignatureHashOriginal`, every row) cannot ride: the loader has no dispatch, it computes
BIP143 for every scope. The alternative is a paste for T3, not this loader: bsv-rs 0.7.0 has a dispatched digest
(`src/primitives/bsv/sighash.rs:970-975`, `compute_sighash_dispatched_for_signing`, internal byte order), and a second
upstream test calling it would carry the 746 table rows, the table's original column and the 18 original-digest
findings. None of the 254 is among bsv-rs's own 500 vectors (`raw_tx`, `script`, `input_index`,
`hash_type` compared).

[D] The findings are at amount 0 because the shape fixes it: `expected_hash` is the BIP143 digest over the node's
scriptCode (`corpus/signer/README.md`; `interpreter.cpp:1471-1481`) at amount 0, not the digest the hand signer
signed. Before writing, the generator recomputes the digest at the row's own amount and requires it to equal the
control digest of the column record, whose signature the node accepted, and recomputes every SDK's recorded digest
over its own scriptCode the same way. The class is marked by its design: bsv-rs v0.7.0 signs over
`script_code.unwrap_or(locking_script)` (`src/script/template.rs:142`, default `None` at `:103`) and the public
override `SigningContext::with_script_code` (`:114-117`) takes the execution-site scriptCode; the caller supplies
the scriptCode (`harness/rules/bsv-rs-signer.json`, ruling `caller-scriptcode-required`). It is not a bug of bsv-rs,
and given the node's scriptCode, bsv-rs computes at amount 0 the digest the generator computes on every finding [X];
the generator's digest at the row's own amount is the control digest the node accepted [D].
